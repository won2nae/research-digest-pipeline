# 임베딩 모델 비교 실험 — bge-m3 vs Qwen3-Embedding-0.6B vs BGE-m3-ko

- **작성일**: 2026-11-17
- **목적**: 현재 프로덕션(`vectorstore.py`)이 쓰는 BAAI/bge-m3 대신 다른 임베딩 모델을 쓰면 검색 품질·속도가 어떻게 달라지는지 실험으로 확인한다.
- **중요**: 이 문서는 실험 결과 보고서다. **프로덕션 적용 여부는 이 결과와 별개로 나중에 결정**하며, 이 실험으로 `vectorstore.py`를 바꾸지 않았다.

## 1. 비교 대상

| 모델 | 특징 |
|---|---|
| **BAAI/bge-m3** (현재 프로덕션) | 8192토큰, 다국어, 1024차원 |
| **Qwen/Qwen3-Embedding-0.6B** | 32,768토큰, 1024차원(32~1024 가변, Matryoshka), Apache 2.0, 다국어(100+) |
| **dragonkue/BGE-m3-ko** | bge-m3를 한국어 검색 데이터로 파인튜닝한 버전. 3rd-party 벤치마크(AutoRAGRetrieval)에서 base bge-m3보다 높은 점수(87.38 vs 83.01) 보고됨 |

## 2. 실험 설계

**왜 전체 아카이브(10만5천 건)가 아니라 2만 건만 썼는가**: 이 실험의 질문은 "같은 조건에서 모델을 바꾸면 검색 품질이 달라지는가"이고, 세 모델이 전부 동일한 코퍼스·동일한 쿼리를 보기 때문에 상대 비교의 타당성은 코퍼스 크기와 무관하다. 모델 3개 × 전체 10만5천 건을 임베딩하는 건 시간이 지나치게 오래 걸리고(bge-m3 1개 모델만으로도 10만 건에 26.5분), 1차 시도에서 실제로 GPU 메모리 부족까지 겪어서(아래 3절) 범위를 좁혔다. 다만 이 선택 때문에 "전체 19년치 아카이브에 대해서도 같은 결론이 성립하는가"는 이 실험만으로는 확인되지 않는다 — 명시적인 한계로 남긴다.

1. **코퍼스**: 2025-01-01 이후 네이버 리포트 20,495건 (`title + content` 그대로, 청크 분할 없음 — 이유는 아래 4절 참고)
2. **쿼리**: 2025-07-01 이후 리포트 중 30건 무작위 샘플링(seed=42, 모델 간 동일)
3. **검색**: 쿼리 자신의 날짜를 look-ahead 방지 컷오프로 써서(프로덕션 `historical_context()`와 동일한 조건), 그 이전 문서들에서만 top-5를 브루트포스 코사인 유사도로 검색
4. **평가**: Claude를 심사자로 써서(이 프로젝트의 기존 LLM-as-judge 방법론, `paperwork/2026-09-14_model_comparison.md`와 동일 계열) 검색된 5개 문서 각각의 관련도를 1~5점으로 채점
5. **지표**: 평균 관련도, Precision@5(3점 이상 비율), 임베딩 처리량(문서/초)

## 3. 1차 시도 — GPU 메모리 부족 사고

최초 구현에서 코퍼스 날짜 필터링 코드에 버그가 있어 의도한 2만 건이 아니라 전체 10만5,640건이 임베딩됐고, 그 상태로 세 모델을 같은 프로세스 안에서 순차 로드하다가 Qwen3-Embedding 로딩 시점에 GPU 메모리가 가득 차 OOM이 발생했다(bge-m3는 완료했으나 이전 모델의 메모리가 완전히 해제되지 않음). 버그를 고치고, 모델마다 완전히 독립된 서브프로세스로 띄워 CUDA 메모리 경계를 프로세스 단위로 강제하도록 재구성해서 재실행했다.

## 4. 임베딩 입력 방식 — 청크 분할을 안 쓴 이유 (참고)

이 프로젝트는 리포트를 청크로 쪼개지 않고 통째로 임베딩한다. 실제 아카이브 105,641건을 bge-m3 토크나이저로 측정한 결과, 평균 298토큰·중간값 236토큰·최대 4,433토큰으로, bge-m3의 한계(8192토큰)를 넘는 문서가 **0건**이었다. 512토큰 기준이면 14.12%(14,918건)가 잘렸을 것 — 즉 "청크 분할 전략을 튜닝"하는 대신 "충분히 긴 컨텍스트를 지원하는 모델을 선택"해서 청크 분할 자체를 불필요하게 만든 결정이며, 실측으로 검증된 선택이다. (Qwen3-Embedding은 32K, BGE-m3-ko는 bge-m3와 동일 토크나이저라 이 결론이 세 모델 모두에 적용된다.)

## 5. 결과

### 5.1 원본 결과

| 모델 | 평균 관련도 | Precision@5(3점↑) | 처리량 |
|---|---|---|---|
| bge-m3 | 3.07/5 | 78.0% | 55건/s |
| Qwen3-Embedding-0.6B | 3.31/5 | 82.7% | 70건/s |
| BGE-m3-ko | 3.21/5 | 78.7% | 54건/s |

### 5.2 이상치 발견과 재검증

원본 결과를 그대로 받아들이기 전에, 쿼리별 세부 점수를 직접 살펴봤다. "유럽 7월 전기차 판매 성장세 확대" 쿼리에서 bge-m3만 5개 후보 전부 0점을 받았는데, 실제 검색된 1위 문서("유럽 전기차 판매 호조세 지속", 2025-06-09)는 다른 두 모델도 똑같이 1~2위로 찾아냈고 거기서는 4~5점을 받았다 — 즉 이건 진짜 품질 차이가 아니라 **심사(Claude 서브프로세스) 호출 실패**로 판단했다.

전체 0점(5개 후보 모두 0점) 쿼리 수를 모델별로 세어보니:

| 모델 | 전체 0점 쿼리 | 전체 30건 중 |
|---|---|---|
| bge-m3 | 4건 | 13.3% |
| Qwen3-Embedding-0.6B | 2건 | 6.7% |
| BGE-m3-ko | 3건 | 10.0% |

채점 실패율이 모델마다 달라서, 실패가 많았던 bge-m3가 원본 결과에서 불리하게 깎인 것으로 보인다. 이 쿼리들을 제외하고(유효 쿼리만) 다시 계산:

| 모델 | 유효 쿼리 수 | 평균 관련도 | Precision@5 |
|---|---|---|---|
| bge-m3 | 26/30 | 3.54/5 | 90.0% |
| Qwen3-Embedding-0.6B | 28/30 | 3.55/5 | 88.6% |
| BGE-m3-ko | 27/30 | 3.56/5 | 87.4% |

## 6. 결론

**검색 품질(관련도·Precision@5)은 세 모델이 통계적으로 구별되지 않는다** (3.54~3.56, n≈27 규모에서 이 차이는 노이즈 수준). 1차 결과에서 보였던 "Qwen3-Embedding이 품질도 앞선다"는 결론은 모델별 채점 실패율 차이가 만든 착시였다.

**유일하게 재현 가능한, 실측 근거가 있는 차이는 처리량이다**: Qwen3-Embedding-0.6B가 70건/s로 bge-m3·BGE-m3-ko(54~55건/s)보다 **약 27% 빠르다.** 이 수치는 채점 파이프라인과 무관하게 측정된 것이라 신뢰도가 높다.

## 7. 한계

- 코퍼스를 최근 2년(2만 건)으로 제한 — 전체 아카이브(19년)에서도 같은 결론이 성립하는지는 미검증.
- 쿼리 30건은 통계적으로 크지 않은 샘플 — 신뢰구간을 엄밀히 구하려면 더 늘릴 필요.
- LLM-as-judge 자체의 호출 실패(약 10%)가 발생했고, 실패 원인(타임아웃·출력 형식 불일치 등)을 구체적으로 분리 조사하지는 않았음 — 재실행 시 judge_batch의 재시도 로직 추가가 다음 개선 과제.
- 프로덕션 적용은 별도 결정 사항 — 이 실험은 "품질은 비슷하니 속도 이점만으로 바꿀 가치가 있는가"라는 질문에 답하기 위한 참고자료.
